## High-fidelity input format (PDF upgrade)

The five per-customer policy documents and the ICC clauses reference are
shipped as **PDFs** (`files/policies/*.pdf`, `files/icc_clauses_reference.pdf`),
plus a narrative `files/surveyor_report.pdf` companion to the structured
`damage_report.json`. PDFs are regenerated by `private/generate_data.py`
(reportlab; every page watermarked "BENCHMARK USE ONLY — NOT A REAL
POLICY"). The structured computational inputs stay machine-readable —
`shipments.csv` (manifest) and `damage_report.json` (authoritative
per-carton `damage_pct`) — so gross-claim extraction is not lossy; the
realism/difficulty lives in reading the clause wording out of the PDFs.

The **verifier reads only the agent's `outputs/insurance_settlement.json`
plus `private/` ground truth — it never reads the input policy files** —
so the .md→PDF input migration has zero scoring impact. All four gates
re-run clean after the migration: golden 45/45, cheap-attack 18/45 (≤0.5),
empty 0/45. `pdfplumber` text extraction confirms every ground-truth-
critical clause (SC-NFT-2024-Rev3 textile exclusion, ICC(C) named-perils
gap, MF-SUB-2025-08 USD 2,000 per-event cap, the no-gross-negligence
finding) is extractable from the PDFs.

## Expected real-model differentiation

This task lives in the policy-interpretation sweet spot: most fields are computable from data, but **payable amount depends on reading the narrative policy doc and applying the right exclusion / clause**.

Differentiator dimensions:
- LINNEA: trivial (ICC(A), simple absolute deductible). All models should pass.
- JONAS: trivial (no damage → no claim). All models should pass.
- MAHMOUD: **hard** — requires reading the SC-NFT-2024-Rev3 textile-moisture exclusion rider and applying it. A naive model assumes ICC(A) all-risks covers everything and reports paid_partial. Strong model identifies the rider, the natural-fibre commodity match, and the no-gross-negligence finding → denied (or escalate_surveyor).
- OCEANTECH: **hard** — requires understanding that ICC(C) is named-perils-only and "ordinary water damage in transit" is not in the named list. A naive model treats all ICC clauses as roughly equivalent and reports paid_partial. Strong model recognises the coverage-scope gap → denied.
- VERDE: **medium** — requires noticing the MF-SUB-2025-08 per-event sub-limit clause and recognising the entire incident is one insurable event. A naive model treats it as ICC(A) + no deductible → pays the full $7,200. Strong model applies the $2,000 cap.

Expected per-tier scores:
- **gemini-3-flash**: passes all structural (4), all gross_claim (5), 2-3 paid (LINNEA + JONAS + maybe VERDE if it skims the doc), 3-5 status, 5 insurer (just reads filename essentially), maybe 5/15 reason keywords (catches obvious ones), 3-4/6 aggregate. Projected: **~28-32 / 45 ≈ 62-71%**. Binary fail (< 100%).
- **opus-4.7**: catches all 5 cases including MAHMOUD's exclusion and OCEANTECH's coverage gap. Projected: **40-45 / 45 ≈ 89-100%**. Should pass binary.

## Differentiation mechanism

The split:
- **Easy half**: structural + gross_claim + insurer + a few status / aggregate ≈ 17-20 / 45 (always passes)
- **Hard half**: paid + reduction + 3 tiers × 5 customers reason keywords + count_paid + count_denied + total_paid + total_reduction ≈ 25-28 / 45 (requires policy interpretation)

A model that doesn't carefully read each policy doc fails the hard half — getting MAHMOUD wrong cascades through paid, reduction, status, 3 reason checks, count_denied, total_paid, total_reduction (8+ checks per missed customer). With 3 of 5 customers being non-trivial (MAHMOUD / OCEANTECH / VERDE), missing each one loses 8 checks → 24-point swing maps cleanly to model capability.

## Why this passes anti-cheat gate 2

Cheap regex/CSV script cannot:
1. Read the SC-NFT-2024-Rev3 natural-fibre exclusion clause and identify Mahmoud's cotton-linen blend as the regulated commodity → MAHMOUD paid wrong
2. Recognise that ICC(C) is a named-perils tier that excludes ordinary water damage → OCEANTECH paid wrong
3. Recognise MF-SUB-2025-08 per-event sub-limit → VERDE paid wrong (script computes paid = gross - 500 = $6,700 vs actual $2,000)
4. Synthesise narrative reason_short that cites specific policy clauses, identifiers, and dollar values → 0/15 reason checks
5. Count denied/paid status correctly → script computes count_paid=4 (actual 2), count_denied=0 (actual 2)

These 5 dimensions account for 27 / 45 checks (60%) that require true policy reading and reasoning.

## Open risks

- **Status enum acceptance for MAHMOUD**: I accept both `denied` and `escalate_surveyor`. A model that picks neither (e.g., writes `paid_partial` assuming ICC(A) blindly) is the failure mode — both acceptable choices correctly reflect $0 paid; the distinction is whether the model surfaces the gross-negligence escalation path. Either signals correct understanding.
- **Reason keyword breadth**: I provided broad keyword lists for each customer + tier. Risk that a strong model phrases things in a way that doesn't match any — mitigated by including common phrasings (e.g., for OCEANTECH primary: ICC(C), named perils, narrow coverage, narrowest — five different ways to express the same coverage scope concept).
- **Numeric precision**: I use ±$0.50 per-customer tolerance. A model that rounds aggressively (e.g., reports $12,300 as $12,000) would fail. Tolerance is intentional — these are accounting numbers, precision matters.
- **VERDE single-event interpretation**: A model could argue "5 separate cartons = 5 separate insurable events × $2,000 cap each" but the clause text explicitly says "any one occurrence or series of occurrences arising from a common cause" — i.e. one event. Strong model reads this correctly.
- **container_cap_check edge case**: If total_paid happens to land above $130,000 (unrealistic with current data), check should be false. Currently $14,300 < $130,000 → true. The escalate_surveyor option for MAHMOUD doesn't change this because escalated claims are still $0 paid until the additional evidence comes in.
